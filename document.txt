American Sign Language Recognition from Processed Landmark Sequences:
Lightweight Temporal Models and Django Web Deployment

Technical Documentation and IEEE Paper Foundation

======================================================================

1. Project Overview
======================================================================

This project implements an end-to-end American Sign Language (ASL)
recognition system for isolated signs. The system uses processed
keypoint sequences rather than raw RGB video. A webcam provides live
video, JavaScript MediaPipe Holistic extracts body and hand landmarks,
and a Django REST Framework endpoint performs PyTorch inference. The
predicted ASL word and its confidence are returned to the browser and
displayed in the user interface.

The target application is real-time, web-based isolated-sign
recognition. The deployed system recognizes a fixed vocabulary of 200
ASL word classes. It is designed to provide a lightweight alternative
to video-heavy action-recognition architectures, with particular
attention to CPU-compatible inference and browser-to-server deployment.

The principal trained models are:

* BiGRU with attention pooling.
* A small Transformer encoder with learnable CLS-token pooling.

The current implementation uses the BiGRU with attention as the
deployment model. The Transformer is trained and evaluated as a
comparison model.

The dataset input is represented as:

    (N, 200, 450)

where N is the number of examples, 200 is the fixed temporal length,
and 450 is the feature dimension at each frame.

The official processed dataset contains 200 classes and the provided
evaluation test split contains 3,552 examples. The reported test
metrics were generated by evaluating the official held-out test split
once, after training and model selection were complete.

======================================================================

2. System Architecture
======================================================================

The complete pipeline is:

    Webcam
      |
      v
    Browser JavaScript
      |
      v
    MediaPipe Holistic landmark extraction
      |
      v
    33 pose + 21 left-hand + 21 right-hand landmarks
      |
      v
    225 position features + 225 velocity features
      |
      v
    200-frame buffer with shape (200, 450)
      |
      v
    JSON POST request to /api/predict/
      |
      v
    Django REST Framework
      |
      v
    PyTorch BiGRU + attention model
      |
      v
    Softmax probabilities over 200 ASL classes
      |
      v
    ID-to-word mapping
      |
      v
    JSON response and browser UI

The browser captures a sequence of exactly 200 frames. The frontend
constructs a singleton batch with shape (1, 200, 450) before sending the
request. The API accepts this explicit batch form and also remains
compatible with a two-dimensional (200, 450) sequence by unwrapping a
singleton batch when necessary.

At server startup, the Django TranslatorConfig loads the trained model
and class-label map. The model is moved to CUDA when CUDA is available;
otherwise it runs on CPU. The model is set to evaluation mode and is
not reloaded for every request.

Inference is enclosed in torch.inference_mode() to avoid autograd
overhead. A process-local threading.Lock serializes model inference.
This provides a conservative protection mechanism for concurrent
requests and makes the deployment behavior explicit. The lock is not a
distributed synchronization mechanism; a multi-process production
deployment would require separate process-level resource planning.

3. Data Preprocessing & Feature Extraction
======================================================================

3.1 Dataset
----------------

The project uses the ASL Citizen 200-word subset distributed as a
processed Hugging Face-style keypoint dataset. The vocabulary contains
200 ASL classes. The processed arrays are stored as sharded NumPy
files and are loaded with memory mapping so that the training scripts
do not concatenate the entire dataset into RAM.

The observed split sizes are:

* Training split: 6,090 examples.
* Validation split: 654 examples.
* Official test split: 3,552 examples.

Training uses only the provided train split. Validation uses only the
provided validation split. The official test split is not used for
training, early stopping, or model selection.

3.2 Fixed temporal window
----------------

Every example is represented by exactly 200 frames. The fixed length
allows the recurrent and Transformer models to receive a consistent
tensor shape without runtime padding inside the PyTorch models.

During web capture, the browser records frames until the buffer
contains exactly 200 feature vectors. The Predict Sign action is
disabled until this condition is met.

3.3 Landmark groups
----------------

Each frame contains three landmark groups:

* Pose: 33 landmarks.
* Left hand: 21 landmarks.
* Right hand: 21 landmarks.

The total is 75 landmarks per frame:

    33 + 21 + 21 = 75 landmarks

Each landmark contributes x, y, and z coordinates:

    75 landmarks x 3 coordinates = 225 position features

The ordering used by the frontend is pose landmarks followed by left
hand landmarks followed by right hand landmarks. This ordering must
remain identical to the ordering used during dataset preprocessing.

3.4 Normalization
----------------

The processed dataset configuration specifies shoulder-center
subtraction and shoulder-width scaling. The frontend mirrors this
operation:

* The midpoint of pose landmarks 11 and 12 is used as the shoulder
  center.
* The shoulder center is subtracted from every landmark coordinate.
* The distance between the two shoulders in the x-y plane is used as
  the scale.
* A fallback scale of 1 is used when the shoulder distance is too small
  to avoid division by zero.

This normalization reduces sensitivity to global translation and
subject scale. It is important that any future data collection client
uses the same landmark ordering, reference landmarks, and scale
definition as the training data.

3.5 Velocity features
----------------

The model input includes temporal motion information in addition to
the normalized landmark positions. For each frame t, the velocity
vector is calculated as:

    velocity_t = position_t - position_(t-1)

The first frame has no predecessor and therefore uses a zero velocity
vector. The final feature vector is:

    [position_t, velocity_t]

with:

    225 position features + 225 velocity features = 450 features

Thus, one captured example has shape:

    (200, 450)

and one model request has shape:

    (1, 200, 450)

3.6 Missing landmark handling
----------------

MediaPipe may fail to detect a hand in individual frames. The
frontend handles missing detections deterministically:

* Missing pose landmarks are replaced with 33 zero-valued
  three-dimensional landmarks.
* Missing left-hand landmarks are replaced with 21 zero-valued
  three-dimensional landmarks.
* Missing right-hand landmarks are replaced with 21 zero-valued
  three-dimensional landmarks.
* Non-finite coordinate values are replaced with zero.

This guarantees 75 landmarks, 225 position features, and 450 total
features for every frame. The backend additionally validates the
resulting shape and rejects non-finite values.

3.7 Split protocol and signer independence
----------------

The project uses the provided train, validation, and test partitions
without creating random splits. The dataset/project protocol describes
these partitions as signer-independent, meaning that signer identity
should not overlap between the training data and the held-out test
data. This is the intended protocol for measuring generalization to
unseen signers.

The local processed metadata confirms the named train, validation, and
test partitions and their sample counts, but does not expose a
dedicated signer/subject column in the manifest fields inspected by
the exploration script. Consequently, the signer-independent property
should be cited as a property of the supplied dataset split protocol,
and should be additionally verified from the original dataset
documentation or signer annotations before making a formal
subject-disjointness claim in a paper.

4. Model Architectures
======================================================================

4.1 BiGRU with attention
----------------

The BiGRU model is the primary deployment model. Its forward path is:

    Input (batch, 200, 450)
      -> LayerNorm over 450 features
      -> Linear projection 450 -> 256
      -> 2-layer bidirectional GRU
      -> Attention pooling over the 200 time steps
      -> Dropout
      -> Linear classifier
      -> 200 class logits

The recurrent configuration is:

* Input size to the GRU: 256.
* Hidden size per direction: 256.
* Number of GRU layers: 2.
* Bidirectional: yes.
* Output size per time step: 512, because the two directions are
  concatenated.
* GRU dropout between recurrent layers: 0.35.

The attention pooling module assigns one scalar score to each of the
200 recurrent outputs. The scores are transformed with a softmax over
time, and the weighted sum of the recurrent sequence produces one
512-dimensional representation for classification. This permits the
model to emphasize informative portions of a sign rather than treating
all frames as equally important.

The classifier uses dropout 0.35 followed by a linear layer from 512
features to 200 class logits.

4.2 Small Transformer encoder
----------------

The comparison Transformer has the following path:

    Input (batch, 200, 450)
      -> LayerNorm over 450 features
      -> Linear projection 450 -> 256
      -> prepend learnable CLS token
      -> add learnable positional embeddings
      -> 3-layer Transformer encoder
      -> select encoded CLS token
      -> Dropout
      -> Linear classifier
      -> 200 class logits

Transformer hyperparameters are:

* Embedding dimension: 256.
* Encoder layers: 3.
* Self-attention heads: 4.
* Feed-forward dimension: 768.
* Activation: GELU.
* Dropout: 0.30.
* Sequence length including CLS token: 201.
* Number of output classes: 200.

The learnable CLS token acts as a global sequence representation. After
the encoder processes the complete sequence, only the encoded CLS
position is passed to the classifier.

4.3 Optimization and regularization
----------------

The BiGRU training configuration is:

* Optimizer: AdamW.
* Learning rate: 3e-4.
* Batch size: 32.
* Dropout: 0.35.
* Loss: CrossEntropyLoss with label_smoothing=0.1.

The Transformer training configuration is:

* Optimizer: AdamW.
* Learning rate: 2e-4.
* Batch size: 32.
* Dropout: 0.30.
* Loss: standard CrossEntropyLoss.

Label smoothing was explicitly used for the BiGRU model. The
Transformer script uses ordinary cross-entropy without label smoothing;
this distinction should be reported accurately in an experimental
section.

======================================================================

5. Model Training
======================================================================

5.1 Data protocol
----------------

The training scripts instantiate separate dataset objects for the
provided train and validation partitions. Shuffling is enabled only
for the training DataLoader. Validation is not shuffled. The test
partition is not loaded by either training script.

The sharded NumPy loader:

* Discovers matching feature and label shards.
* Validates that each feature shard has shape (N, 200, 450).
* Validates feature/label row-count equality.
* Uses memory-mapped arrays.
* Converts individual examples to float32 PyTorch tensors.

The random seed is set to 42 for Python, NumPy, and PyTorch. The
training scripts support argparse options for dataset root, epochs,
patience, batch size, worker count, seed, and checkpoint output.

5.2 Early stopping and checkpointing
----------------

The default maximum number of epochs is 100 and the default early
stopping patience is 12 epochs. After each training epoch, the model
is evaluated on the validation partition. The checkpoint with the
lowest validation loss is copied and saved after training.

The checkpoints are:

* models/best_bigru_attention_model.pt
* models/best_transformer_model.pt

Each checkpoint contains the model state dictionary, model
configuration, and best validation loss.

5.3 Runtime and epoch duration
----------------

The training scripts print device, sample counts, loss, accuracy, and
epoch number. In the recorded run, training was performed on CPU and
the BiGRU run stopped early after epoch 50. The recorded run achieved
its best validation behavior during that training process.

Per-epoch wall-clock duration was not recorded by the training
scripts, so no numerical epoch-time claim is made here. Actual
duration depends on CPU model, number of workers, memory bandwidth,
PyTorch build, and whether CUDA is available. A publishable paper
should report hardware and measured training time if runtime
comparisons are required.

5.4 Leakage control
----------------

The test set is excluded from all training and validation operations.
The evaluation script loads the test split only after both best
checkpoints exist. It performs one test DataLoader pass and retains
the resulting predictions for metric calculation and confusion
matrices.

======================================================================

6. Evaluation & Results
======================================================================

6.1 Evaluation protocol
----------------

Both best checkpoints were loaded in evaluation mode. The official
held-out test split contains 3,552 samples. The evaluation script
evaluated that test split once, with both models producing predictions
from the same test batches.

The metrics are:

* Top-1 accuracy: the fraction of examples whose highest-probability
  class is correct.
* Top-5 accuracy: the fraction of examples whose correct class occurs
  among the five highest-probability classes.
* Macro F1-score: the unweighted mean of per-class F1 scores across
  all 200 classes.

6.2 Results comparison
----------------

| Model                    | Top-1 Accuracy | Top-5 Accuracy | Macro F1-Score |
|--------------------------|----------------|----------------|----------------|
| BiGRU + Attention        | 97.10%         | 99.30%         | 97.13%         |
| Small Transformer        | 97.02%         | 99.58%         | 96.92%         |
| I3D baseline             | ~63%           | Not reported   | Not reported   |

The I3D baseline value is the approximate Top-1 result supplied for
the original ASL Citizen paper comparison. Top-5 and Macro F1 values
for that baseline were not provided and are therefore not fabricated.

6.3 Interpretation
----------------

The BiGRU has the highest Top-1 accuracy and Macro F1-score among the
two implemented models. This indicates strong overall classification
performance and balanced behavior across the 200-class vocabulary.
The Transformer has a slightly higher Top-5 accuracy, indicating that
its correct class is marginally more likely to appear among its five
highest-ranked candidates even though its Top-1 and Macro F1 values
are slightly lower.

Top-5 accuracy is particularly relevant to a retrieval-oriented web
application. In an interactive system, the backend can expose a
ranked candidate list, allow a user or downstream language model to
resolve ambiguity, or use the candidate set as input to later
contextual decoding. A high Top-5 score means that the correct sign is
available to such a second-stage component even when the first-ranked
word is incorrect. Top-5 accuracy does not replace Top-1 accuracy for
direct user-facing prediction, but it measures useful retrieval
quality for practical interfaces.

The reported test results should be treated as final only for the
specified checkpoint and preprocessing pipeline. Any change to
landmark normalization, landmark ordering, model weights, or split
definitions requires a new evaluation.

7. Why It Is Better (Scientific Novelty)
======================================================================

The main contribution is an efficient keypoint-based temporal
recognition pipeline rather than a claim that the underlying
classification problem has been solved universally.

7.1 Comparison with a heavy I3D baseline
----------------

The original ASL Citizen comparison includes a heavy I3D-style
spatiotemporal video baseline with an approximate reported Top-1
performance of 63%. The present system instead operates on
MediaPipe-derived pose and hand keypoints. The supplied implementation
achieves 97.10% Top-1 accuracy for the BiGRU + Attention model and
97.02% for the small Transformer on the specified processed test
split.

These numbers should not be interpreted as a perfectly controlled
like-for-like benchmark unless the original baseline and the present
models use identical data partitions, preprocessing, and evaluation
conditions. Nevertheless, the comparison motivates the efficiency
benefit of representation-level modeling.

7.2 Background suppression
----------------

Raw video contains background texture, lighting variation, camera
motion, clothing, and other visual factors that are not essential to
the articulated sign motion. Landmark preprocessing removes most of
this pixel-level nuisance variation before temporal modeling. The
models therefore focus on normalized body and hand geometry and its
motion.

7.3 Computational efficiency
----------------

The deployed model receives a compact tensor of 200 time steps by
450 scalar features rather than a sequence of high-resolution video
frames. The BiGRU is lightweight enough to be deployed with PyTorch
on CPU in the Django process, subject to normal server capacity
constraints. The Transformer comparison also uses a compact
256-dimensional representation, three encoder layers, four heads,
and a 768-dimensional feed-forward block.

The web system demonstrates that real-time-style capture and
server-side inference can be implemented without requiring an
I3D-sized video model. A formal paper should include measured
latency, throughput, memory use, and parameter counts if it claims a
quantitative efficiency advantage. Those measurements are not
recorded in the current training and deployment scripts.

7.4 Reproducible deployment-oriented design
----------------

The project connects the same feature contract across three layers:

* Dataset preprocessing creates 450 features per frame.
* JavaScript reproduces the 225-position plus 225-velocity contract.
* Django validates the request shape before PyTorch inference.

This explicit contract reduces a common source of deployment failure:
training and serving pipelines that use different landmark ordering,
normalization, or temporal feature definitions.

8. Web Application Deployment
======================================================================

8.1 Django REST Framework backend
----------------

The Django app uses TranslatorConfig.ready() to load the model and
label map during application initialization. The deployment checkpoint
is:

    models/best_bigru_attention_model.pt

The repository's current label-map fallback is:

    metadata/id_to_label.json

The backend also supports the intended deployment path:

    models/label_map.json

The API endpoint is:

    POST /api/predict/

The expected request is:

    {
      "sequence": [
        [450 values],
        "... 200 frames total ..."
      ]
    }

The frontend sends the explicit singleton batch form internally as
(1, 200, 450). The API validates the sequence, converts it to a
float32 NumPy array, rejects non-finite values, and converts it to a
PyTorch tensor on the selected device.

The response is:

    {
      "word": "predicted_word",
      "confidence": 0.95
    }

The confidence is the maximum softmax probability for the predicted
class. It is a model probability estimate, not a calibrated
probability guarantee.

8.2 Thread-safe inference
----------------

Inference executes inside a process-local threading.Lock and
torch.inference_mode(). The lock prevents overlapping access to the
shared global model object within the Django process. inference_mode
prevents gradient tracking and reduces unnecessary CPU/memory work
during prediction.

For production scaling, the deployment should measure the effect of
the lock under concurrent load. Multiple worker processes will have
separate model copies and separate locks. A production configuration
should therefore account for memory usage, worker count, request
timeouts, and queueing behavior.

8.3 Frontend capture and buffering
----------------

The template uses MediaPipe Holistic through browser JavaScript. It
captures webcam frames, extracts pose and hand landmarks, applies the
same shoulder-centered normalization, computes frame-to-frame
velocity, and appends the resulting 450-element vector to a buffer.

The buffer stops recording once it reaches 200 frames. The Predict
Sign button is then enabled. Before the request, the frontend checks:

* Outer batch length is 1.
* Sequence length is 200.
* Every frame length is 450.

The buffer is copied into a singleton batch, sent as JSON, and the
camera is stopped before inference. Clear / Reset removes all frames,
resets the previous-position state, and permits a new recording.

The interface includes a loading spinner and console diagnostics for
frame shape, input batch shape, and API response values. These
diagnostics support debugging of browser-to-server feature-contract
mismatches.

9. Limitations & Future Work
======================================================================

9.1 Isolated vocabulary scope
----------------

The system recognizes a fixed 200-word isolated-sign vocabulary. It
does not perform continuous sentence translation, grammatical
decoding, word segmentation, or sign-to-English sequence generation.
A user must provide a temporal window corresponding to one isolated
sign.

9.2 Facial and non-manual features
----------------

The deployed feature contract explicitly includes pose, left-hand, and
right-hand landmarks. Facial expressions and other non-manual
markers are not explicitly modeled in the 450-dimensional feature
vector. This may limit recognition of signs whose meaning depends on
facial expression, eyebrow position, mouth shape, or head pose beyond
the selected body landmarks.

9.3 Dataset and signer verification
----------------

The project follows the supplied split protocol and does not create
random splits. However, the local manifests inspected by the
exploration script do not contain a dedicated signer identifier
field. A publishable study should verify signer disjointness directly
from authoritative dataset annotations and report the exact protocol.

9.4 Real-world robustness
----------------

MediaPipe detection quality can degrade under occlusion, unusual
camera angles, low light, motion blur, multiple people, or missing
hands. Zero-padding provides a deterministic input shape but does not
recover information that was not detected. The web application
should therefore communicate confidence and capture status rather
than treating every low-confidence prediction as reliable.

9.5 Calibration and uncertainty
----------------

The returned confidence is the largest softmax score. No calibration
method, abstention threshold, or out-of-distribution detector is
implemented. Future work should evaluate calibration, selective
prediction, confidence thresholds, and rejection of unknown signs.

9.6 Evaluation scope
----------------

The reported results are for the provided 3,552-example official test
split and the two saved checkpoints. Additional experiments are
needed for cross-dataset generalization, demographic variation,
camera variation, vocabulary expansion, and continuous signing.

9.7 Future research directions
----------------

Recommended extensions include:

* Continuous ASL recognition with temporal segmentation and CTC or
  sequence-to-sequence decoding.
* Explicit facial and head landmarks for non-manual signals.
* A language-model or retrieval reranker using Top-5 candidates.
* Quantization, TorchScript, ONNX, or browser-side inference.
* Measured CPU latency, throughput, memory footprint, and parameter
  counts under realistic concurrent requests.
* Signer-disjoint cross-validation and confidence calibration.
* Robustness testing under occlusion, lighting, viewpoint, and
  missing-landmark conditions.
